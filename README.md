# SE-Principles


| ویژگی کیفی         | معنی ساده و مستقیم                                                                 |
|--------------------|-------------------------------------------------------------------------------------|
| Interoperability   | تعامل‌پذیری – توانایی ارتباط با سیستم‌ها و نرم‌افزارهای دیگر                       |
| Reusability        | قابلیت استفاده مجدد – استفاده دوباره از کد یا ماژول در پروژه‌های دیگر              |
| Portability        | قابل انتقال بودن – اجرا در سیستم‌های مختلف بدون تغییر زیاد                         |
| Flexibility        | انعطاف‌پذیری – سازگاری آسان با تغییر نیازها یا افزودن امکانات جدید                 |
| Testability        | قابلیت آزمون – امکان تست آسان برای اطمینان از درستی عملکرد                         |
| Maintainability    | قابلیت نگهداری – سهولت در اصلاح، تغییر و به‌روزرسانی نرم‌افزار                     |
| Usability          | قابلیت استفاده – راحتی استفاده برای کاربر، رابط کاربری ساده                        |
| Integrity          | یکپارچگی – حفظ امنیت و صحت داده‌ها، جلوگیری از دستکاری غیرمجاز                     |
| Efficiency         | کارایی – عملکرد سریع با مصرف کم منابع سیستم                                         |
| Reliability        | قابلیت اطمینان – اجرای پایدار و بدون خطا حتی در شرایط سخت                          |



| شماره | عنوان                              | توضیح ساده و مفهومی                                                                                  |
|-------|------------------------------------|--------------------------------------------------------------------------------------------------------|
| 1     | انواع نیازهای نرم‌افزار            | عملکردی (چه کاری انجام دهد)، کیفی (چطور انجام دهد)، محدودیت‌ها (مثلاً زبان برنامه‌نویسی)              |
| 2     | واکنش معماری به نیازها             | طراحی باید هم عملکرد و هم کیفیت را پوشش دهد؛ محدودیت‌ها باید در طراحی لحاظ شوند                      |
| 3     | رابطه معماری با کیفیت             | یک رویداد ممکن است چند کیفیت را تحت تأثیر قرار دهد؛ برخی ویژگی‌ها با هم تضاد دارند                   |
| 4     | مفهوم کیفیت                        | کیفیت یعنی رضایت کاربران؛ دیدگاه مشتری، توسعه‌دهنده و مدیر ممکن است متفاوت باشد                      |
| 5     | کنترل و تضمین کیفیت               | کنترل: یافتن خطا پس از تولید؛ تضمین: جلوگیری از خطا با فرآیند صحیح و استاندارد از ابتدا              |
| 6     | هزینه کیفیت                        | شامل هزینه پیشگیری، ارزیابی، شکست داخلی (قبل ارائه)، شکست خارجی (بعد از ارائه)                       |
| 7     | مدل McCall                         | مجموعه‌ای از ویژگی‌ها مثل اطمینان، کارایی، استفاده‌پذیری، نگهداری، انتقال‌پذیری و...                  |
| 8     | کیفیت طراحی و اجرا                | طراحی خوب یعنی برنامه‌ریزی قوی؛ اجرای خوب یعنی پیاده‌سازی دقیق مطابق طراحی                          |
| 9     | نکات مهم در کیفیت                  | کیفیت باید قابل سنجش، مستند، استاندارد و حتی پنهان مثل راحتی استفاده باشد                             |
| 10    | تضمین کیفیت نرم‌افزار (SQA)       | فرآیندهایی مثل بازبینی، مستندسازی، مدیریت خطا و نظارت برای بالا نگه داشتن کیفیت پروژه               |
| 11    | بازبینی فنی رسمی (FTR)            | جلسه بررسی فنی گروهی برای کشف خطا، بهبود مستندات، رعایت استاندارد و افزایش دقت تیم                 |
| 12    | تضمین کیفیت آماری                 | تحلیل داده‌های خطا برای یافتن ریشه‌ها و بهبود فرآیند توسعه نرم‌افزار                                 |
| 13    | دلایل رایج خطا                     | مشخصات ناقص، تفسیر اشتباه، کدنویسی نادرست، رعایت نکردن استانداردها                                   |
| 14    | قابلیت اطمینان و دستیابی          | اطمینان: نرم‌افزار بدون خطا کار کند؛ دستیابی: همیشه در دسترس باشد (با محاسبات MTTF، MTTR)             |
| 15    | استاندارد ISO 9001                | چارچوب رسمی تضمین کیفیت شامل مستندسازی، کنترل تغییر، بازبینی قرارداد و سایر فرآیندهای کنترل کیفیت    |



## McCall Model:
| ویژگی              | دسته           | توضیح ساده و مستقیم                                                 |
|--------------------|----------------|----------------------------------------------------------------------|
| Correctness        | عملیاتی        | نرم‌افزار کار درست را انجام دهد و نیازهای تعریف‌شده را برآورده کند |
| Reliability        | عملیاتی        | نرم‌افزار بدون خطا و پایدار کار کند                                 |
| Efficiency         | عملیاتی        | سرعت بالا و مصرف منابع کم داشته باشد                                |
| Integrity          | عملیاتی        | از دسترسی یا تغییرات غیرمجاز جلوگیری کند (امنیت و انسجام)          |
| Usability          | عملیاتی        | کار کردن با نرم‌افزار برای کاربر آسان باشد                         |
| Maintainability    | قابل نگهداری   | به‌راحتی بتوان آن را تغییر، به‌روزرسانی یا اصلاح کرد               |
| Flexibility        | قابل نگهداری   | به‌راحتی بتوان ویژگی یا قابلیت جدیدی به آن اضافه کرد               |
| Testability        | قابل نگهداری   | بتوان نرم‌افزار را راحت و دقیق تست کرد                              |
| Portability        | انتقالی        | بتوان آن را روی سیستم‌ها یا پلتفرم‌های مختلف اجرا کرد              |
| Reusability        | انتقالی        | بخش‌هایی از نرم‌افزار را بتوان در پروژه‌های دیگر استفاده کرد       |
| Interoperability   | انتقالی        | بتواند با نرم‌افزارها و سیستم‌های دیگر تعامل داشته باشد           |


## OOP slide concepts
| 🔹 عنوان | 🔍 توضیحات |
|---------|------------|
| مقدمه: چرا مهندسی نرم‌افزار شیء‌گرا؟ | در دهه ۶۰ میلادی (کنفرانس NATO 1968) با بالا رفتن پیچیدگی سیستم‌های نرم‌افزاری، نیاز به روشی مهندسی برای ساخت سیستم‌های قابل نگهداری و توسعه احساس شد. |
| بحران نرم‌افزار | روش‌های قدیمی نمی‌توانستند پیچیدگی را کنترل کنند، به همین دلیل نیاز به مهندسی نرم‌افزار به وجود آمد. |
| مشکلات توسعه نرم‌افزار | هزینه‌های بالا، تأخیر در تحویل، نیازهای مبهم، کیفیت پایین، یکپارچه‌سازی سخت، نگهداری پرهزینه. |
| تفاوت برنامه‌نویسی و مهندسی نرم‌افزار | برنامه‌نویسی فقط نوشتن کد است. مهندسی نرم‌افزار شامل تحلیل، طراحی، تست، مستندسازی و نگهداری است. مثل تفاوت ساخت قفسه DIY با ساخت پل. |
| اصول مهندسی نرم‌افزار شیء‌گرا: توسعه تکراری و تدریجی | پروژه به تکرارهای کوچک تقسیم می‌شود، هر تکرار بخشی از سیستم را می‌سازد و تست می‌کند. بازخورد سریع، کاهش ریسک، انعطاف بالا. |
| اصول شیء‌گرا: مدیریت نیازمندی‌ها | نیازمندی یعنی چیزی که سیستم باید داشته باشد. باید ردیابی، اولویت‌بندی و مدل‌سازی شود. |
| معماری مبتنی بر مؤلفه‌ها | سیستم به اجزای مستقل تقسیم می‌شود. امکان استفاده مجدد، انعطاف بالا، کاهش پیچیدگی، جداسازی وظایف. |
| مدلسازی تصویری | استفاده از UML برای نمایش رفتار و ساختار سیستم به شکل گرافیکی، حذف ابهام در تیم. |
| بررسی مستمر کیفیت | کیفیت باید از اول تا آخر بررسی شود، با معیارهای مشخص. هدف: کشف زودهنگام خطاها. |
| مدیریت تغییرات و پیکربندی | تغییر اجتناب‌ناپذیر است. باید افراد مجاز، زمان و نحوه‌ی تغییرات را مدیریت کرد. |
| اصول شیء‌گرایی: تجرید | نادیده گرفتن جزئیات پیاده‌سازی برای تمرکز روی ویژگی‌های اصلی. مثال: کلاس ماشین بدون جزئیات موتور. |
| اصول شیء‌گرایی: محصورسازی | مخفی کردن داده‌ها داخل کلاس، فقط از طریق متدها قابل دسترسی. کنترل دسترسی و امنیت بیشتر. |
| اصول شیء‌گرایی: پیمانه‌بندی | تقسیم سیستم به ماژول‌هایی با وظایف مستقل. بهبود سازمان‌دهی و نگهداری. |
| اصول شیء‌گرایی: سلسله‌مراتب | رابطه‌ی بین کلاس‌ها (ارث‌بری) یا اجزای داخلی سیستم (مثلاً موتور بخشی از ماشین است). |
| فرآیند توسعه نرم‌افزار چیست؟ | مجموعه‌ای از فعالیت‌های نیمه‌مرتب برای رسیدن به هدف، با فضای خلاقیت. برخلاف فرآیند خشک سنتی. |
| USDP چیست؟ | یک فرآیند توسعه نرم‌افزار مبتنی بر شیء‌گرایی. شامل معماری‌محوری، موردکاربری‌محوری، توسعه تدریجی. |
| فازهای USDP | 1. Inception (آغاز) – تعیین محدوده  2. Elaboration (تشریح) – تحلیل معماری  3. Construction (ساخت) – پیاده‌سازی  4. Transition (انتقال) – تحویل نهایی |
| RUP چیست؟ | متدولوژی اجرایی USDP با دو بعد: عمودی (گردش‌کارها)، افقی (فازهای زمانی) |
| نظم‌ها (Disciplines) در RUP | تحلیل و طراحی، مدیریت نیازها، آزمون، پیاده‌سازی، استقرار، تغییر، مدیریت پروژه، مدل‌سازی کسب‌وکار، محیط توسعه |
| نقدهای وارد بر RUP | پیچیده، سنگین، مناسب پروژه‌های بزرگ، مدل‌سازی زیاد، عدم توجه کافی به طراحی پایگاه داده، نقش‌های نامشخص |


| عنوان                        | توضیح کامل |
|-----------------------------|------------|
| تعریف چابکی                 | روشی برای توسعه نرم‌افزار با تمرکز بر پاسخ سریع به تغییرات، تحویل مداوم، کار گروهی و حداقل‌سازی کارهای غیرضروری مانند مستندسازی. |
| بیانیه چابک                 | 1. افراد و تعاملات > ابزارها و فرآیندها  <br> 2. نرم‌افزار عملیاتی > مستندسازی جامع <br> 3. همکاری با مشتری > قرارداد رسمی <br> 4. پاسخ به تغییر > پیروی از یک طرح |
| اصول دوازده‌گانه چابک       | 1. رضایت مشتری با تحویل مداوم <br> 2. استقبال از تغییر <br> 3. تحویل نرم‌افزار هر چند هفته <br> 4. همکاری دائم با مشتری <br> 5. تیم باانگیزه و محیط اعتماد <br> 6. ارتباط چهره‌به‌چهره <br> 7. نرم‌افزار اجرایی = پیشرفت <br> 8. توسعه پایدار با سرعت ثابت <br> 9. طراحی خوب و کیفیت فنی <br> 10. سادگی <br> 11. تیم‌های خودسازمانده <br> 12. بازبینی رفتار برای بهبود |
| زمان مناسب استفاده از چابک | مناسب برای پروژه‌های با تغییر زیاد، تیم‌های نزدیک و مشتری در دسترس، پروژه‌های کوچک تا متوسط، مهارت برنامه‌نویسی بالا، مستندات کم. |
| XP - Extreme Programming     | متدولوژی چابک با تأکید بر کیفیت کد، تست‌محوری، ارتباط قوی با مشتری. فعالیت‌های اصلی: TDD، برنامه‌نویسی زوجی، طراحی تدریجی، مالکیت جمعی. |
| ارزش‌های XP                 | ارتباط، سادگی، بازخورد، شجاعت، احترام. |
| فعالیت‌های XP               | داستان‌های کاربری، طراحی تکاملی، TDD، برنامه‌نویسی زوجی، کار پرانرژی، محیط کاری نزدیک، مالکیت جمعی. |
| نقش‌های XP                  | برنامه‌ساز، مشتری (User)، آزمون‌گر، پیگیر (Tracker)، مربی (Coach). |
| TDD (توسعه آزمون‌محور)       | 1. نوشتن تست قبل از کد <br> 2. اجرای تست و شکست اولیه <br> 3. نوشتن حداقل کد <br> 4. Refactor کردن کد |
| Scrum                        | چارچوب چابک با ساختار زمان‌دار (Sprint)، تعامل بالا با ذینفعان، تأکید بر تحویل تدریجی محصول قابل استفاده. |
| ارزش‌های Scrum              | شجاعت، تمرکز، تعهد، احترام، صداقت و شفافیت. |
| نقش‌های Scrum               | مالک محصول (Product Owner)، اسکرام مستر (Scrum Master)، تیم توسعه (Development Team). |
| فرآورده‌های Scrum           | Product Backlog، Sprint Backlog، Increment. |
| رویدادهای Scrum             | 1. برنامه‌ریزی Sprint <br> 2. جلسه روزانه (Daily Scrum) <br> 3. بازبینی Sprint <br> 4. جلسه بازتاب (Retrospective) |
| Kanban                       | چارچوب سبک و بصری برای مدیریت جریان کار. شروع از وضعیت فعلی، بدون تغییر ساختار تیم، تأکید بر بهبود تدریجی. |
| اصول Kanban                 | شروع از وضعیت فعلی، بهبود مداوم، نقش‌های منعطف، سیاست‌های شفاف، بازخورد منظم، محدود کردن WIP. |
| ویژگی‌های تخته Kanban       | دارای ستون‌های قابل تعریف (مثل: در حال انجام، آماده تست)، نمایش اقلام کاری، امکان محدود کردن اقلام در هر ستون. |
| مقایسه XP, Scrum, Kanban    | **XP**: تمرکز بر کد و مهندسی، ساختار آزاد، جلسات کم. <br> **Scrum**: تمرکز بر مدیریت پروژه، ساختار زمان‌دار، جلسات زیاد. <br> **Kanban**: تمرکز بر جریان کار، بدون جلسات رسمی، ساختار بسیار انعطاف‌پذیر. |
| نتیجه‌گیری                  | چابکی یعنی پاسخ به تغییر. هیچ روش واحدی بهترین نیست. می‌توان روش‌ها را ترکیب کرد (مثل: استفاده از Daily Scrum + TDD). |
